# opensend.cc v2.0.0

## Highlights

- Send and receive WhatsApp, Messenger and Instagram messages alongside email.
- Handle WhatsApp Calling with browser agents, IVR menus and AI voice bots.
- Send, list and read all four message channels through one `/messages` API.
- Manage email domains and Meta senders on one Channels page.
- Start automations from every supported channel event. Use event fields in filters, messages and later steps.
- Send broadcasts over email, WhatsApp, Messenger and Instagram, within each channel's rules.
- Create Custom API keys with separate read and write scopes.
- Use the SDK and MCP tools for the v2 API, including calling, knowledge, tools and contact notes.

**Anonymous usage statistics are on by default, including after an upgrade without a saved preference.** Turn sharing off in setup or instance settings, pass `--telemetry no` to the installer, or set `OPENSEND_TELEMETRY=0` for a locked hard off. See [what is sent and how to opt out](../telemetry.md).

## New

### Messaging and channels

Connect WhatsApp Business numbers, Facebook Pages and Instagram accounts to a team. Read and reply in Playground → Inbox. Sending and Receiving show delivery logs for all four channels.

WhatsApp supports text, templates, media, stickers, reactions, interactive messages and the supported business message types. Templates can be submitted to Meta and synced back with approval and quality status. Messenger and Instagram have local text and quick-reply templates.

Contacts can have a phone number without an email address. Their channel identities, notes and recent messages stay together in Audience. CSV imports accept email or phone columns. Exports include linked channel identities.

### Calling and voice

Receive WhatsApp calls through a browser softphone, an IVR menu or a voice bot. Place outbound bot and IVR calls from the dashboard, API or an automation after the contact grants calling permission. Requesting permission does not place a call automatically.

Build IVR menus with prompts, keypad choices, business hours, voicemail and handoffs. Automations and IVRs share a visual flow editor. Test menus and bots from Playground before assigning them to a number.

Voice bots use your team's AI provider keys. Add knowledge bases, collect structured answers and map them to contact properties. Give a bot signed webhook tools to look up information in your own service. Review transcripts, summaries, tool results, collected answers and optional recordings. ElevenLabs voice choices come from your own account.

IVR signing secrets are shown once after creation or rotation. Copy the secret before closing the dialog. Rotate it in the dashboard, with `POST /ivrs/{id}/rotate-signing-secret`, with the SDK's `ivrs.rotateSigningSecret`, or with the MCP tool `rotate-ivr-signing-secret`. Rotation requires `ivrs:write`.

Browser agents can use an optional TURN relay on strict networks. They receive one-hour credentials that refresh before expiry. The installer configures your own coturn for STUN and TURN. TLS TURN is available with a trusted certificate and an extra port mapping. The shared TURN secret stays on the server.

### Automations, broadcasts and integrations

Use message, delivery, contact and call events as automation triggers. Filter on their fields and reuse trigger or previous-step values. Send follow-ups on another channel or place a permitted call.

WhatsApp broadcasts use approved templates. Messenger and Instagram broadcasts use local templates and reach contacts with an open 24-hour conversation window. Delivery rechecks that window; recipients whose window has closed are skipped.

The event catalog describes trigger fields and webhook payloads. Search custom event names and page through definitions. Saved automation triggers and their field schemas remain available beyond the first page. Contact notes, direct media uploads, connected accounts, conversations, call permissions, IVRs, providers, knowledge and bot tools have API, SDK and MCP coverage. Existing email and channel-specific methods remain available.

### Anonymous usage statistics

opensend.cc sends schema 1 statistics to `https://opensend.cc/api/telemetry` after setup and then daily. The payload contains only:

- A random, persistent installation ID, the send timestamp, installed version and installation age in whole days.
- Deployment details: self-hosted or Convex Cloud, install method (`script`, `compose`, `source` or `unknown`), architecture (`amd64`, `arm64` or `unknown`) and a calling-enabled flag.
- Usage bands for teams, team memberships, verified domains, enabled automations, webhook endpoints, API keys, connected WhatsApp numbers, Messenger Pages, Instagram accounts, IVRs and voice bots.
- Usage bands for sent and received emails, API requests, SDK requests, MCP requests and channel messages over the latest complete 24 hours; broadcasts and calls created in the past 30 days, including test calls.
- Whether SES has production access (`null` if unknown), SMTP was used in the past 30 days and any team enforces SSO.

Every usage count uses `0`, `1-9`, `10-99`, `100-999`, `1k-9k` or `10k+`. Exact feature counts are never sent. Email, API and channel counts use complete 15-minute intervals. SDK and MCP counts are recognized subsets of API requests.

The payload never contains email addresses, names, domains, hostnames, IP addresses, team or user IDs, message content, keys or URLs. There are no browser tracking scripts or page-load events. **View what's sent** in instance settings previews the payload without contacting the collector. The [telemetry guide](../telemetry.md) lists every schema field and explains the controls.

## Improved

- Templates and message previews show rendered content, including saved WhatsApp template text and Messenger or Instagram quick replies.
- Channel identities stay tied to the right Page, account or WhatsApp caller. Known callers are available to a bot from the start of a call.
- Transcripts stay in time order and keep caller turns through interruptions. New tool events use the same call timeline.
- Calls have clearer outcomes, a floating call card and controls that remain available while navigating.
- Search reaches bots, IVRs, tools, knowledge bases and provider keys beyond the first page. Knowledge documents and provider keys have pagination.
- Mobile pages, flow canvases, tabs, labels and subscription controls are easier to read and use.
- Broadcast reports wait for their metrics. Audience review distinguishes loading, an error and an empty audience before allowing a send.
- Voice calls check tool limits without reading the full transcript for every tool request. Older calls initialize their counters once.
- New broadcast recipient and contact-history pages read fewer related records. Message statuses stay current; older records remain readable without a manual migration.
- Sending, Receiving and Inbox searches bound the content they load while preserving continuation through all results.
- Screen readers get clearer field names, search labels, dialog titles and navigation landmarks. Switches and calendar dates outside the current month have clearer contrast.
- The installer backs up data before upgrades and can add calling with prebuilt images. Saved settings and secrets carry forward.
- Files use Convex storage and direct upload URLs. Self-hosters can configure Convex's S3-compatible storage backend.

## Fixed

### Security fixes

- Meta error messages mask echoed app secrets, access tokens, signup codes and verification tokens before reaching logs or the dashboard.
- IVR read responses and API logs mask signing secrets. This includes older IVR responses displayed from logs.
- Values in unquoted email HTML attributes cannot add extra attributes through whitespace or delimiters.
- Team limits protect tool tests, knowledge indexing and searches, WhatsApp template publishing and manual sync, SSO discovery and forced voice-catalog refreshes. Failed provider requests also consume the allowance.
- Embedding requests reject redirects and oversized responses. Attachment downloads close discarded responses instead of leaving connections open.
- Email webhook previews no longer expose body text. They use the subject; authenticated message reads still provide the body.
- Browser calling leases are revoked on tab close and presence expiry. Credential refresh keeps the presence expiry job active.
- Delayed automation events cannot recreate a deleted contact or bind to a replacement contact with the same address.

### Reliability fixes

- Gateway calls left connected after a lost callback end automatically. Once heartbeat support is confirmed, two minutes without recorded audio activity starts expiry. Older gateways use a two-hour fallback. Checks run once a minute; API-managed calls are excluded.
- Ending a call releases its agent and call reservations even if Meta credentials are missing or remote cleanup fails. Late callbacks cannot leave ended calls connected or count their duration twice.
- Accepted calls survive a racing setup timeout. Failed voice sessions end cleanly, and a duplicate session cannot release another session's reservation.
- Large webhook deliveries and Meta callback batches finish in smaller batches. Duplicate delivery workers are rejected. Repeated delivery or read updates no longer emit the same milestone or regress message status.
- Queued channel broadcasts and automation messages recheck recipient eligibility before sending. Unsubscribed or deleted contacts and changed audience preferences are respected.
- Failed channel media downloads retry and then show an error instead of remaining pending.
- Reconnected accounts route to the current team and account. Disconnecting large connections cleans up all senders without affecting a later reconnect.
- Learned WhatsApp phone numbers link historical conversations to the existing contact. Deleting a contact keeps its channel history and removes the old contact link. Late reactions cannot hide newer reactions.
- Fixed garbled bot audio, slow hang-up and IVR prompt quality on WhatsApp calls.
- Fixed caller matching for WhatsApp business-scoped identities.
- Fixed automation calls that ignored resolved trigger and previous-step values.
- Bounded unified message reads so large bodies can be paginated without losing rows.
- Prevented the softphone from crashing unrelated pages before a team or SSO session is ready.
- Deleted voice bots, knowledge bases and IVRs show a missing-record state. An IVR assigned to calling settings must be unassigned before deletion.
- Fixed channel reply routing, historical template previews, stale call ringing and lost Inbox filters on mobile.

## Breaking or behaviour changes

Review these before updating clients or operating the new channels.

### Contact responses and shared lists

Contact API responses now include `phone`. `email` can be `null`, including for contacts created from Meta messages. Contact event payloads also allow a missing email. Update validators and code that assumes every contact has an email address. Creating a contact through the API still needs an email address or phone number.

`GET /templates` can return templates from all four channels. Use `?channel=email` for an email-only list. Existing email templates may omit `channel`; treat that as email. `GET /broadcasts` can also return all channels. Check `channel` before reading email content; an omitted channel means email. Meta records carry their channel settings and may have empty email fields.

API key list rows add `permission` and `scopes`. Automation run-step responses add nullable `inputs`, showing the values used by that step. Allow these additions if your client validates responses against a closed schema.

### Permissions and errors

Full access and Sending access keys keep their existing roles. Sending access remains email-send-only. It does not grant message reads or Meta sends. Custom keys need the relevant `resource:read` or `resource:write` scope; write includes read. API key management, usage and OAuth grant management still need Full access.

Insufficient permission now returns HTTP `403` with `restricted_api_key`. Restricted API keys previously returned `401`; OAuth scope failures previously used `invalid_permission`. Update error handling for both status and name.

For new integrations, calls, routing, permissions and transcripts use `calling:*`. Provider keys use `voice_providers:*`. The earlier broad `whatsapp:*` and `voice_bots:*` grants still cover these operations respectively. Replace broad grants if you want separate access. A Custom key's domain restriction applies to email writes; it does not restrict its other resource scopes.

### Moving to `/messages`

Moving an email client to `/messages` is optional. Existing `/emails` routes remain. `/messages` reads return `object: "message"`, `channel`, `direction`, `preview` and nullable `contact_id`. Email recipients remain an array. Send responses are `{ id }`.

`GET /messages` uses `cursor` and returns `next_cursor`, alongside `data` and `has_more`. Keep the same filters and readable channels when continuing. A short or empty page can still have more results. Continue until `next_cursor` is `null`. The existing resource lists use `after` or `before` instead.

Unfiltered message lists return only channels the key can read. An explicit channel filter, an individual read or a send requires that channel's scope. Do not expect a WhatsApp-only key to see email rows.

### Webhooks and secrets

Email and channel message events include common message fields alongside their existing fields. Allow the added fields in strict webhook validators. Email `preview` is the subject, not body text. Fetch content through authenticated API reads when needed.

AI provider key and bot-tool writes are redacted in API request logs. Saved provider keys and bot-tool secrets are not returned by their read APIs. Keep the original secrets in your own secret store rather than reading them back from opensend.cc.

IVR reads no longer return the signing secret. Get, list, update and render responses keep `webhook_signing_secret` but return `"[redacted]"`. Save the real secret from creation or rotation in your own secret store. Rotation invalidates the old secret immediately; update the service verifying IVR webhooks. If the original secret is lost, rotate it instead of reading it back.

Before deleting an IVR assigned to a number, change that number's calling route. Deletion is refused while calling settings still reference the IVR.

### Event catalog and operation limits

`GET /events/catalog` keeps `object: "event_catalog"` and `data`, and adds `has_more` and `next_cursor`. It returns a page rather than every custom definition. Use `limit` (default 20, maximum 100), `after` and optional `search`. Pass `next_cursor` as `after` until `has_more` is false, keeping the search unchanged. System events are included in addition to the custom-event limit on the first page. Backward pagination is not supported. Update SDK and MCP clients for these options.

Teams can define at most 10,000 custom event types. The limit also applies when saving an automation creates a definition. Existing definitions above the cap remain usable. Delete unused definitions to make room. During the automatic upgrade backfill, teams with existing definitions briefly cannot add new ones; reading, sending, updating and deleting existing definitions still works.

High-volume tool tests, indexing, searches, template operations and SSO discovery now share limits across a team. Allow for rejected operations even when switching tools or API entry points. Forced ElevenLabs refreshes are limited to once per minute per team and return `429 voice_catalog_rate_limited` when exhausted; cached reads remain available.

Connected gateway calls now expire after two minutes without recorded activity once heartbeat support is confirmed. Gateways without heartbeat support use a two-hour fallback. Upgrade the gateway with the backend and check that active calls keep reporting activity. Allow for the activity write allowance of up to 30 seconds and the once-a-minute cleanup check. API-managed calls are excluded.

If a call ends while a remote connection is being accepted, the late connect request returns `409 call_ended`. Do not treat it as a connected call or retry acceptance blindly.

New broadcast recipients keep the channel identity shown when the send was queued. Later identity profile edits do not rewrite that historical display. Contact details and message statuses still update.

### Dashboard destinations

Messages replaces the Emails navigation label. The dashboard still uses `/emails` for its message logs.

Domains now opens Channels filtered to email: `/domains` redirects to `/channels?type=email`. Domain detail URLs remain available. `/settings/ses` redirects to `/instance/ses`.

Inbox and Calls live in Playground. `/emails/inbox` and `/emails/calls` redirect there and preserve query parameters. Update bookmarks and browser scripts. The Messages tab strip has Sending, Receiving and Suppressions; it has no Inbox or Calls tab. Channel message details have a Preview tab and an Open in Inbox link, with the conversation below the preview.

### Self-hosting and earlier v2 installs

Docker Compose 2.24.4 or newer is required. Calling is optional. The installer now uses prebuilt calling images and supplies backend settings when you opt in. Prepare public media ports, a stable public IPv4 address and a trusted calling certificate first. Scripted calling requires local Convex; Convex Cloud needs a separately secured gateway connection.

Earlier TURN installs must replace `CALL_TURN_PASSWORD` with `CALL_TURN_SECRET` and matching coturn shared-secret authentication. The installer generates the new secret and removes the old password. Manual installs must update both coturn and Convex, then reconnect browser agents.

Anonymous usage statistics default to on when an upgraded installation has no saved preference. Use the setup or instance settings switch, install with `--telemetry no`, or set `OPENSEND_TELEMETRY=0` in the backend for a locked hard off. Compose forwards that environment setting through the migrate service. Framework telemetry switches do not control these statistics.

If you ran an earlier v2 calling build with shared browser passwords, rebuild and restart FreeSWITCH between calls. The current directory accepts temporary authorized sessions and has no static-user fallback.

If you used an earlier v2 application-level S3, R2 or MinIO provider, its routes and migration runner are removed. Files now use Convex storage. Legacy records with a Convex `storageId` still work. Object-only files need their bytes recovered into Convex. A Convex export cannot back up objects held only by the removed provider.

Earlier v2 direct-upload clients must POST file bytes to the returned Convex upload URL, then submit its `storageId` receipt as `storage_id` to the completion endpoint. The upload response reports `provider: "convex"`. Replace any earlier presigned PUT flow. See [file upload instructions](../object-storage.md#direct-uploads-and-limits).

## Upgrade notes

Follow the [v1 → v2 upgrade guide](../upgrade-v1-to-v2.md) for script and Compose installs, backups, calling, checks and rollback.

Back up the database, file bytes, configuration and encryption keys before changing versions. The installer stops the local stack and archives the mounted Convex data volume and old configuration before upgrading. Cloud installs take a file-inclusive export. Keep image overrides aligned with the release. The migration container applies backend settings, deploys functions and schema, and starts the automatic custom-event counter backfill. The script upgrade also requests the resumable historical count backfill. New search indexes can lengthen deployment while they build.

Email-only installations can upgrade without setting up Meta or calling.

## Known limitations

- Real Meta delivery and calling require your own eligible Meta app, accounts and permissions. Automated QA uses test providers; complete the [live checklist](../qa/live-checklist.md) on your own accounts. App Review, business verification, Tech Provider onboarding and calling eligibility are external requirements.
- Embedded Signup needs a WhatsApp configuration ID and the dashboard domain allowed in your Meta app. Facebook Login for Page connections needs its own configuration ID. Manual token connections are available when signup is not configured.
- Free-form Meta messages require an open service window. WhatsApp templates require approval. Messenger and Instagram broadcasts have no path around their 24-hour window; they do not use message tags to extend it.
- Agents behind strict networks may need the optional TURN relay. Public firewall rules and trusted WSS certificates still need a real network test. TLS TURN needs its own certificate and port mapping. TURN relays browser-agent media; it does not relay the Meta side of a call.
- Script-enabled calling can be reported as disabled in anonymous statistics: the installer saves `yes`, while the telemetry flag requires backend `OPENSEND_CALLING=1`.
- Calling setup lists at most 100 connected WhatsApp numbers and reads their settings separately. Older broadcast recipient/history rows still use extra lookups. Large-team latency remains a concern; no production speed guarantee is implied by the read bounds.
- The installer does not wire recording files into the backend's recording reader. Recording ingestion needs separate runtime configuration. Back up recordings and certificates separately from Convex data.
- If Meta accepts a send but the worker stops before saving the provider message ID, the local message can appear failed even though it arrived. Check the recipient or provider before resending; an automatic retry could duplicate the message.
- Captured signed Meta or SES callbacks can be accepted again after deduplication records expire (seven and 30 days respectively). Other message and status checks can prevent repeat effects, but callback freshness is not enforced.
- CSV formula protection has an unverified edge case when a spreadsheet strips leading whitespace. The QA review has not confirmed its behaviour in real spreadsheet applications.
- Historical duplicate provider message IDs across accounts remain a lookup edge case. Normal provider collisions have not been demonstrated.
- A full browser accessibility review is still pending. The shared control labels and contrast fixes do not establish that every screen meets accessibility requirements.
- Channel call-log rows do not link to call detail. Open Playground → Calls for the full record.
- Corrupt stored channel-message JSON can still break its detail page. The dashboard review did not reproduce such corruption. Caller-context relative times also use different wording from general dashboard times.
- File download URLs grant bearer access and do not expire automatically. Direct upload URLs have no storage-level size cap; the application checks size when completing an upload. Uploaded bytes with no completion receipt need operator cleanup.
- Historical transferred-bot tool timestamps are not backfilled. New events use the corrected call timeline.
- The checked-in OpenAPI YAML has incomplete descriptions and examples, plus incorrect oversized-request response references for knowledge and bot tools. Use the [enriched OpenAPI export](../qa/dx-parity.md#limits-and-lead-verification) when generating client documentation.
