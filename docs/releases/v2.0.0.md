# opensend.cc v2.0.0

## Highlights

- Send and receive WhatsApp, Messenger and Instagram messages alongside email.
- Handle WhatsApp Calling with browser agents, IVR menus and AI voice bots.
- Send, list and read all four message channels through one `/messages` API.
- Manage email domains and Meta senders on one Channels page.
- Start automations from every supported channel event. Use event fields in filters, messages and later steps.
- Send broadcasts over email, WhatsApp, Messenger and Instagram, within each channel's rules.
- Create Custom API keys with separate read and write scopes.
- Use the SDK and MCP tools for the v2 API, including calling, knowledge, tools and contact notes.

## New

### Messaging and channels

Connect WhatsApp Business numbers, Facebook Pages and Instagram accounts to a team. Read and reply in Playground → Inbox. Sending and Receiving show delivery logs for all four channels.

WhatsApp supports text, templates, media, stickers, reactions, interactive messages and the supported business message types. Templates can be submitted to Meta and synced back with approval and quality status. Messenger and Instagram have local text and quick-reply templates.

Contacts can have a phone number without an email address. Their channel identities, notes and recent messages stay together in Audience. CSV imports accept email or phone columns. Exports include linked channel identities.

### Calling and voice

Receive WhatsApp calls through a browser softphone, an IVR menu or a voice bot. Place outbound bot and IVR calls from the dashboard, API or an automation after the contact grants calling permission. Requesting permission does not place a call automatically.

Build IVR menus with prompts, keypad choices, business hours, voicemail and handoffs. Automations and IVRs share a visual flow editor. Test menus and bots from Playground before assigning them to a number.

Voice bots use your team's AI provider keys. Add knowledge bases, collect structured answers and map them to contact properties. Give a bot signed webhook tools to look up information in your own service. Review transcripts, summaries, tool results, collected answers and optional recordings. ElevenLabs voice choices come from your own account.

### Automations, broadcasts and integrations

Use message, delivery, contact and call events as automation triggers. Filter on their fields and reuse trigger or previous-step values. Send follow-ups on another channel or place a permitted call.

WhatsApp broadcasts use approved templates. Messenger and Instagram broadcasts use local templates and reach contacts with an open 24-hour conversation window. Delivery rechecks that window; recipients whose window has closed are skipped.

The event catalogue describes trigger fields and webhook payloads. Contact notes, direct media uploads, connected accounts, conversations, call permissions, IVRs, providers, knowledge and bot tools have API, SDK and MCP coverage. Existing email and channel-specific methods remain available.

## Improved

- Templates and message previews show rendered content, including saved WhatsApp template text and Messenger or Instagram quick replies.
- Channel identities stay tied to the right Page, account or WhatsApp caller. Known callers are available to a bot from the start of a call.
- Transcripts stay in time order and keep caller turns through interruptions. New tool events use the same call timeline.
- Calls have clearer outcomes, a floating call card and controls that remain available while navigating.
- Search reaches bots, IVRs, tools, knowledge bases and provider keys beyond the first page. Knowledge documents and provider keys have pagination.
- Mobile pages, flow canvases, tabs, labels and subscription controls are easier to read and use.
- Broadcast reports wait for their metrics. Audience review distinguishes loading, an error and an empty audience before allowing a send.
- Files use Convex storage and direct upload URLs. Self-hosters can configure Convex's S3-compatible storage backend.

## Fixed

### Security fixes

- Email webhook previews no longer expose body text. They use the subject; authenticated message reads still provide the body.
- Browser calling leases are revoked on tab close and presence expiry. Credential refresh keeps the presence expiry job active.
- Delayed automation events cannot recreate a deleted contact or bind to a replacement contact with the same address.

### Reliability fixes

- Fixed garbled bot audio, slow hang-up and IVR prompt quality on WhatsApp calls.
- Fixed caller matching for WhatsApp business-scoped identities.
- Fixed automation calls that ignored resolved trigger and previous-step values.
- Bounded unified message reads so large bodies can be paginated without losing rows.
- Prevented the softphone from crashing unrelated pages before a team or SSO session is ready.
- Deleted voice bots, knowledge bases and IVRs show a missing-record state. An IVR assigned to calling settings must be unassigned before deletion.
- Fixed channel reply routing, historical template previews, stale call ringing and lost Inbox filters on mobile.

## Breaking or behaviour changes

Review these before updating clients or operating the new channels.

### Contact responses and shared lists

Contact API responses now include `phone`. `email` can be `null`, including for contacts created from Meta messages. Contact event payloads also allow a missing email. Update validators and code that assumes every contact has an email address. Creating a contact through the API still needs an email address or phone number.

`GET /templates` can return templates from all four channels. Use `?channel=email` for an email-only list. Existing email templates may omit `channel`; treat that as email. `GET /broadcasts` can also return all channels. Check `channel` before reading email content; an omitted channel means email. Meta records carry their channel settings and may have empty email fields.

API key list rows add `permission` and `scopes`. Automation run-step responses add nullable `inputs`, showing the values used by that step. Allow these additions if your client validates responses against a closed schema.

### Permissions and errors

Full access and Sending access keys keep their existing roles. Sending access remains email-send-only. It does not grant message reads or Meta sends. Custom keys need the relevant `resource:read` or `resource:write` scope; write includes read. API key management, usage and OAuth grant management still need Full access.

Insufficient permission now returns HTTP `403` with `restricted_api_key`. Restricted API keys previously returned `401`; OAuth scope failures previously used `invalid_permission`. Update error handling for both status and name.

For new integrations, calls, routing, permissions and transcripts use `calling:*`. Provider keys use `voice_providers:*`. The earlier broad `whatsapp:*` and `voice_bots:*` grants still cover these operations respectively. Replace broad grants if you want separate access. A Custom key's domain restriction applies to email writes; it does not restrict its other resource scopes.

### Moving to `/messages`

Moving an email client to `/messages` is optional. Existing `/emails` routes remain. `/messages` reads return `object: "message"`, `channel`, `direction`, `preview` and nullable `contact_id`. Email recipients remain an array. Send responses are `{ id }`.

`GET /messages` uses `cursor` and returns `next_cursor`, alongside `data` and `has_more`. Keep the same filters and readable channels when continuing. A short or empty page can still have more results. Continue until `next_cursor` is `null`. The existing resource lists use `after` or `before` instead.

Unfiltered message lists return only channels the key can read. An explicit channel filter, an individual read or a send requires that channel's scope. Do not expect a WhatsApp-only key to see email rows.

### Webhooks and secrets

Email and channel message events include common message fields alongside their existing fields. Allow the added fields in strict webhook validators. Email `preview` is the subject, not body text. Fetch content through authenticated API reads when needed.

AI provider key and bot-tool writes are redacted in API request logs. Saved provider keys and bot-tool secrets are not returned by their read APIs. Keep the original secrets in your own secret store rather than reading them back from opensend.cc.

IVR `webhook_signing_secret` is still returned by authenticated IVR reads in this version. It is not masked or write-only. Treat those responses as secret-bearing data and restrict `ivrs:read` access.

Before deleting an IVR assigned to a number, change that number's calling route. Deletion is refused while calling settings still reference the IVR.

### Dashboard destinations

Messages replaces the Emails navigation label. The dashboard still uses `/emails` for its message logs.

Domains now opens Channels filtered to email: `/domains` redirects to `/channels?type=email`. Domain detail URLs remain available. `/settings/ses` redirects to `/instance/ses`.

Inbox and Calls live in Playground. `/emails/inbox` and `/emails/calls` redirect there and preserve query parameters. Update bookmarks and browser scripts. The Messages tab strip has Sending, Receiving and Suppressions; it has no Inbox or Calls tab. Channel message details have a Preview tab and an Open in Inbox link, with the conversation below the preview.

### Self-hosting and earlier v2 installs

Calling is optional and requires separately built services, public media ports and backend settings. The standard installer does not build those services or set their backend variables. Browser agents need a trusted calling certificate.

If you ran an earlier v2 calling build with shared browser passwords, rebuild and restart FreeSWITCH between calls. The current directory accepts temporary authorized sessions and has no static-user fallback.

If you used an earlier v2 application-level S3, R2 or MinIO provider, its routes and migration runner are removed. Files now use Convex storage. Legacy records with a Convex `storageId` still work. Object-only files need their bytes recovered into Convex. A Convex export cannot back up objects held only by the removed provider.

Earlier v2 direct-upload clients must POST file bytes to the returned Convex upload URL, then submit its `storageId` receipt as `storage_id` to the completion endpoint. The upload response reports `provider: "convex"`. Replace any earlier presigned PUT flow. See [file upload instructions](../object-storage.md#direct-uploads-and-limits).

## Upgrade notes

Follow the [v1 → v2 upgrade guide](../upgrade-v1-to-v2.md) for script and Compose installs, backups, calling, checks and rollback.

Back up the database, file bytes, configuration and encryption keys before changing versions. The installer saves configuration copies but does not export your data for you. Keep image overrides aligned with the release. The migration container applies backend settings and deploys functions and schema; historical count backfills are a separate command. New search indexes can lengthen deployment while they build.

Email-only installations can upgrade without setting up Meta or calling.

## Known limitations

- Real Meta delivery and calling require your own eligible Meta app, accounts and permissions. Automated QA uses test providers; complete the [live checklist](../qa/live-checklist.md) on your own accounts. App Review, business verification, Tech Provider onboarding and calling eligibility are external requirements.
- Embedded Signup needs a WhatsApp configuration ID and the dashboard domain allowed in your Meta app. Facebook Login for Page connections needs its own configuration ID. Manual token connections are available when signup is not configured.
- Free-form Meta messages require an open service window. WhatsApp templates require approval. Messenger and Instagram broadcasts have no path around their 24-hour window; they do not use message tags to extend it.
- Agents behind networks that block direct media may need TURN. The optional relay does not configure the dashboard automatically. Supplying relay credentials to the browser adapter remains operator work. The bundled relay has no TLS TURN listener, and it does not relay the Meta side of a call.
- The event catalogue returns all definitions in one response. Very large custom event catalogues can exceed response limits. There is no paginated catalogue yet.
- Calling setup lists at most 100 connected WhatsApp numbers and reads their settings separately. Large contact broadcast-history pages also read related records per row. Latency at that scale remains a concern in the backend review.
- Channel call-log rows do not link to call detail. Open Playground → Calls for the full record.
- Corrupt stored channel-message JSON can still break its detail page. The dashboard review did not reproduce such corruption. Caller-context relative times also use different wording from general dashboard times.
- File download URLs grant bearer access and do not expire automatically. Direct upload URLs have no storage-level size cap; the application checks size when completing an upload. Uploaded bytes with no completion receipt need operator cleanup.
- Historical transferred-bot tool timestamps are not backfilled. New events use the corrected call timeline.
- The checked-in OpenAPI YAML has incomplete descriptions and examples, plus incorrect oversized-request response references for knowledge and bot tools. Use the [enriched OpenAPI export](../qa/dx-parity.md#limits-and-lead-verification) when generating client documentation.
