Wave 6C backend hardening audit — base `586ea51`, branch `codex/lane-6c`.

The audit inventoried 233 directly registered public query/mutation/action definitions, including the isolated Better Auth component. It traced app entry points through their authorization helpers and component calls, inspected the HTTP routers, scheduled callbacks, retention writers, validators, and imported token/network helpers. Component functions are callable through the app, not directly by dashboard clients; their caller-supplied session IDs come from verified JWTs in the app wrapper. No new tables, routes, screens, AWS permissions, or schema migrations were introduced. UI and e2e files were untouched.

The remaining `v.any()` uses are dynamic payloads rather than a known fixed return shape: recursive editor documents (`tables/templates.ts`, `templates.ts`, `tables/broadcasts.ts`, `broadcasts.ts`), arbitrary custom-event data (`tables/automationEvents.ts`, `api/events.ts`, `tables/automations.ts`), heterogeneous event/webhook envelopes (`tables/events.ts`, `tables/webhooks.ts`, `webhooks.ts`), and provider-specific email-event details (`tables/emails.ts`). Producer validation and existing byte limits remain in place; tightening persisted recursive values needs a compatibility/data review. The known-null workflow context was tightened without a migration.

Authorization review found no confirmed missing team guard allowing a caller to fetch or modify another team's product row. Single-ID functions load a row to derive its organization and then authorize before returning or modifying it. Functions accepting both organization and document IDs check ownership or use organization-scoped indexes/namespaces. Product commands continue allowing plain members; team administration and installation operations retain their existing role checks. Tests include plain-member writes, cross-team refusal containing “permission”, and invalid input. The Better Auth component's three pagination sites all use `paginator(ctx.db, schema)`; no additional native component pagination was found. No production `.collect()` calls were found outside the unused README example.

HTTP review covered `http.ts`, all `api/*` route families, auth/OAuth, SMTP, SNS, tracking, unsubscribe, and received-file downloads. SNS ingestion uses configured topic lookup, restricted certificate URLs, signature verification, and topic/message deduplication. Token helpers use distinct signing contexts; unsubscribe verifies team/contact ownership, file tokens bind email/attachment and expire, and tracking now rejects retired teams. The existing SSRF fetcher checks and pins public DNS addresses, including redirect validation. Method routing and REST authentication/rate limits remain unchanged. Fixed body-size limits are noted above; public signed-file downloads and SNS signature handling still rely on edge/operator traffic controls for volumetric abuse.

The deterministic authorization scan covered identity-from-argument, document ownership, sensitive query returns, and parent references on writes. Candidate app functions using delegated checks were followed into the existing helpers instead of introducing a parallel authorization system. The audit also reviewed scheduled generation/claim checks, duplicate SNS processing, broadcast recipient deduplication, and automation event/run deduplication. This is a static plus mocked-runtime audit, not a deployment or real-AWS certification.

The existing API-key creation response contract was checked against [Resend's create-key reference](https://resend.com/docs/api-reference/api-keys/create-api-key). Batch and response budgets were checked against [Convex's transaction and HTTP limits](https://docs.convex.dev/production/state/limits). Local installed Convex/convex-helpers/workflow code was used for implementation details.
