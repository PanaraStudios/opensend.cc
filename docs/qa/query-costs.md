# Dashboard query read-cost audit

Audited on `perf/v2-dashboard-queries`, 2026-10-06. Inventory starts with `rg -n 'api\.|useQuery|usePaginatedQuery|useTeamQuery' components app`, follows imported hooks in `lib/`, `useTeamList` (list + count), `useQueries`/metric chunks, and `watchQuery`. Public actions/mutations are excluded. The table includes all 150 reachable public queries, including onboarding, auth, unsubscribe, and one-shot export download queries so these edges are not missed. Sources link to the exported handler; the consumer column records one representative call site. Helpers and component handlers were read as well, particularly `lists.ts`, `counts.ts`, `channels/templates.ts`, `channels/rows.ts`, `audience.ts`, `api/paging.ts`, `betterAuth/{teams,policy,oauth}.ts`, and the resource/list helpers.

These are source-based estimates of **database reads per execution**, not measured latency or exact billing. Scenario: 50k contacts, 200k messages, 5k recipients per broadcast, 1k templates, 1k custom events, 100 configured topics/properties, 10 domains/connected accounts normally, and 20-step automations. P=40 initial ordinary list rows (UI also supports 80/120); L=25 resource rows unless consumer uses 100. E=custom event definitions; K=automation step keys; D=domain count; Q=prompts per IVR; W=webhook event types. Headers/contacts/definitions ≈0.5–2 KiB; event schemas ≈1–4 KiB; bodies ≈30 KiB normally, 256 KiB in regressions, and up to the 1 MiB document limit. Unicode, properties, graph size, payloads, and attachments alter these estimates substantially.

`A(k)` means k aggregate range/count operations, **not k documents**. The mounted aggregate components read namespace trees and B-tree nodes, with lazy roots and logarithmic boundary traversals. Allow roughly 2–30 nodes and 2–120 KiB per nonempty range at this scale as a conservative planning model; empty ranges and batched/cache-shared traversals can cost much less. Actual populated-tree metrics are required before declaring aggregate-heavy charts fast. Counts are maintained through `insertRow`/`patchRow`/`deleteRow` in the source mutation transaction. Unsupported count filters intentionally return `{total:null}` rather than scan.

All team-authenticated rows additionally read session, user, indexed membership, organization and SSO (usually 5 documents / a few KiB, plus proof for enforced SSO). Admin authorization usually reads session/user/bootstrap. Those dependencies can invalidate otherwise narrow subscriptions on session/profile/organization/SSO changes. Repeated nested calls may repeat these checks. Product costs below exclude this common overhead unless it dominates the query.

A document projection does **not** reduce stored bytes read or exclude other fields from invalidation. Indexed pagination limits the inspected range, not merely the returned array; changes to documents/insertions in that range can invalidate even when post-filtered out. Writes to another team are excluded by team prefixes, except the explicitly noted global/admin and account-scope paths. Aggregates may rerun on shared ancestor-node changes outside the exact requested key range within the namespace. Most append-only newest-page subscriptions necessarily rerun on new matching rows. Native `numItems` is a target, not a hard reactive limit: endCursor replay/splits can expand a page. Search helpers retain all incoming pagination metadata and apply explicit scan budgets; byte budgets can overshoot by one scanned/reserved item and merged-source lookahead. Ordinary native pagination is marked watch where bodies or large hydration make that expansion significant.

`fine` = indexed bounded work at the scenario; `watch` = bounded but significant bytes, nested fan-out, hot dependencies, or reactive-page expansion; `fix` = clear linear/unsafe read path. Fixed rows retain their original verdict and show the current state. Calling/voice/IVR handlers were inspected read-only, as requested.

## Changes and remaining work

The fix for `messages.sending`, `messages.receiving`, and `conversations.list` reserves 4 MiB per retained template-message or Inbox search match through the existing `filteredPage`/`SearchStream` budget, before hydration starts. This covers typical content/published-body reads, historical name lookup fan-out, and account/person headers with headroom. Sparse searches still scan their existing indexed batch; dense searches return shorter pages with continuation/split metadata, so no result is discarded. Non-search pagination and all query return validators are unchanged. `convex/queryCosts.test.ts` exercises actual public Convex queries with 120 matching messages and 256 KiB payloads under explicit nested 2 MiB / 40-document transaction limits, checks rendered values, traverses all message continuations without omissions/duplicates, and replays endCursor with stricter row/byte limits. This is a regression bound for that fixture, not a universal 2 MiB production guarantee: the reservation is conservative and the stream budget permits one-item overshoot. The shared helper now also accepts a per-row reservation: email hits reserve zero downstream bytes, and plain channel messages reserve 2 KiB for contact hydration. Regressions verify that both plain-message queries still return eight requested matches under the same tight limits. Inbox headers do not carry the latest message type, so they conservatively reserve template hydration. The helper already had constant reservation support for template thumbnails; these callers were missing it.

`automationEvents.catalog` remains an unbounded `collect()` of custom definitions. Silently capping it would remove trigger/wait variable schemas and alter the editor’s behavior. Preserving every schema requires paginated consumption (or fetching only the current graph’s referenced event names); the existing no-argument shared hook in `components/dashboard/automations/references.tsx` does neither. Requested permission for minimal pagination wiring because the user’s component restriction only permits call-site pagination arguments, which is insufficient for consuming/combining all pages with an unchanged catalog array return contract. Pending that permission, leave the handler/data intact and classify **fix**, not fine. No write-time cap was imposed on public REST event definitions.

No schema/index change or new component was needed for the implemented search fixes. Existing body separation already protects message header lists from body writes, and counters already replace whole-team row counts. A new staged index would require backfill and a later deploy before queries could use it; none was added merely as unused groundwork.

Remaining watches: broadcast list rows share fan-out cursor/settlement fields; template picker metadata is rewritten on autosave; the account snapshot reads capped rosters to compute capped member counts; thread bubbles read whole email bodies for 4000-character snippets; native reactive pages with bodies can expand on endCursor replay; large charts multiply aggregate ranges by channels/statuses/days/steps/domains. Splitting broadcast operational fields while preserving every exposed raw-row value would require a compatibility projection (which would reintroduce list dependencies) or a separate list contract, so this audit records the hot dependency without silently dropping public fields. Time-dependent query helpers (`usage`, reputation, auth invitations/session expiry, thread normalized controls, claims, export URLs, and default metrics ranges) also use wall clocks; these are cache/freshness watches rather than row scans and should be addressed with explicit time arguments or scheduled flags in their owning lanes.
