# Opensend REST contract

[opensend.yaml](opensend.yaml) describes the handlers at `0b10d8d`, using OpenAPI 3.1 and Resend operation IDs/schema names where applicable. The Resend-derived material is MIT licensed; retain [LICENSE-resend](LICENSE-resend) and the YAML attribution comment. The source snapshot’s SHA-256 is embedded in the spec and the [parity report](../docs/resend-parity.md).

Set the server variable `apiOrigin` to the installation’s Convex HTTP action/site origin, without a trailing slash. This is different from the dashboard origin. The contract covers 72 operations: 70 through `apiRoute`, plus the two legacy OAuth grant resource routes. OAuth grant routes have separate token, response, error and pagination behavior; their operation-level security overrides the default bearer scheme. Authentication protocols, tracking, unsubscribe and signed downloads are excluded explicitly in the coverage test.

Run `pnpm test:auth convex/openapi.test.ts` for focused validation, or `pnpm test:auth` for the full backend suite. The test:

- captures application route registrations and checks coverage in both directions, including direct OAuth routes and an explicit list of excluded protocol routes;
- validates the OpenAPI document with Swagger Parser and compiles request/response JSON schemas with Ajv 2020;
- sends authenticated requests through Convex test fixtures and validates real email, domain, contact and template responses, plus authorization/validation errors;
- rejects unexpected response fields and pauses background jobs, with AWS and network calls mocked.

Update the spec alongside handler changes; do not loosen schemas just to accommodate an unexplained failure. Response schemas use required fields and disallow undocumented properties. Request objects generally permit unknown fields because current handlers ignore them; explicit forbidden fields and state-dependent validation are documented separately. Timestamps from `apiTime` are PostgreSQL-style strings, so they are not annotated as RFC 3339 `date-time`. Cross-field totals, UTF-8 byte limits, stored template defaults and authorization checks still require backend validation.

The [parity report](../docs/resend-parity.md) compares all 113 operations in the supplied upstream snapshot and records SDK behavior separately. Its served count excludes common differences from classification; it is not a count of fully identical endpoints. Reconcile this base contract with lane 7A’s implementation changes during integration.

## WhatsApp Cloud API catalog

`POST /whatsapp/messages` accepts exactly one catalog body. The same schemas drive REST validation and MCP input schemas, and the SDK exposes `SendWhatsAppMessageOptions`. Use `to` for a phone/wa_id or `recipient` for a business-scoped user id (BSUID); `to` takes precedence when both are present. BSUID identities are scoped to the connected Meta business and linked to a CRM contact when a phone becomes known. Authentication templates targeting a BSUID return 422 when the template is synced locally; unsynced template definitions and account capabilities are checked by Meta.

Every list, detail and customer message event includes `type`, typed `content`, `raw`, and `identity`, with optional `context`, `referral`, `errors`, `attachments`, `reactions` and `reaction_target_id`. Existing scalar `text`, per-type fields, and detail `media` arrays remain available. Locally resolved templates also include their existing `rendered` snapshot with header, body, footer and button labels. Narrow the SDK's `WhatsAppMessage` or `WhatsAppMessageDetail` by `type` to read `content`. `raw` retains the Meta message/send payload; `send_response` retains Meta contacts, optional user_id/wa_id, message ids and template pacing. Status observations retain `status_raw`, including opaque callback data. `played` follows `read`; payment observations emit `whatsapp.message.payment_updated` and retain `payment` without changing delivery status.

The send operation has named request and queued-response examples for every send type, interactive subtype and template parameter/button variant. The detail operation has inbound examples and `sent_*` examples. The OpenAPI `whatsappMessage` webhook has corresponding customer event examples, plus played and payment observations. The real-shaped fixtures in `lib/meta/whatsapp-fixtures.json` are exercised through Convex REST/webhooks, the SDK, MCP, and the OpenAPI schemas.

Media in root messages, template parameters and interactive/carousel headers appears in `attachments` with signed download URLs. URLs expire after one hour; re-read the message to refresh them. Download URLs may return 404 while asynchronous fetching is pending. WhatsApp media-id downloads refresh Meta's expiring URL and authenticate with the bearer token. Public outbound media links use the guarded fetcher without the Meta token. Local uploads are checked against the selected message type and voice-note format; external media ids/URLs still require Meta to verify MIME, dimensions and codecs. Structural limits, aggregate list/product limits, carousel consistency and known reaction target age/deletion are validated before enqueueing with clear 422 errors. Calling enablement/quota, catalog ownership, regional payment availability, payment transitions, and approved template definitions remain provider checks.

Polls cannot be sent through the Cloud API; poll_creation/poll_update are received as unsupported messages with raw data preserved. There is no separate video-note flag: video notes use `video`. GIF template headers belong to the Marketing Messages API. Footers, phone-number, request-contact-info and SPM template buttons are static parts of approved definitions and need no invented send parameter. Dashboard rendering and composers are deferred to Task 7a-2.

Static template components and send parameters follow Meta’s [template components](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/components) and [product carousel send syntax](https://developers.facebook.com/documentation/business-messaging/whatsapp/catalogs/product-card-carousel-template-messages).
